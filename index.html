2. How Anthropic works

  1. Server does the work — commits/merges/diff/blame server-side; sparse or no checkout. Scale: 2,500 → 30,000 merges/day, ~25M checkouts/day.
  2. Changeset, not branch — delta vs first parent, lock-free, cost ∝ change. Refs discouraged; only main matters.
  3. Derived data — blame/history computed recursively from parents, added without client changes.
  4. Intent review (Antique) — humans review intent, semantic approvals, tell Claude "no" on constraint violations.
  5. No merge queue — post-merge + pre-deploy tests; agents fix conflicts.
  6. Superfans — one Claude per component watching telemetry in Slack.
  7. Quality by simulation — hermetic sims, fuzzing, rate limiting.
  8. 7 people, 5 months — Scion + Antique + ~6 systems, while merges grew 10×.

Don't copy: new VCS, Spanner, blob caches, virtual FS. Keep git.

4. Try it: simulated harness

Same state machine as Phases 0–2, in-memory. Watch exactly-once submit, parallel forks, approval memo, crash/resume, and auto-fix on failed landing.

5. Build phases

  1. Phase 0 — Durability spike: SQLite harness, kill mid-tool → resume() finishes; same requestId ≠ duplicate.
  2. Phase 1 — Vibe loop: 3 forks, own worktrees, cheap triage / strong implementer; abort cascades.
  3. Phase 2 — Antique-lite: Plan/Review docs, approval hook, landing task, auto-fix fork.
  4. Phase 3 — Superfans: background watchers, compaction/handoff, multiplayer watch().
  5. Phase 4 — Guardrails when pain appears: restartLimit parked tasks, idempotency keys, hot-swap extensions.

6. Risks

  • Pi Durable is experimental — pin the version.
  • One process owns one storage — multi-machine needs Durable Objects, not shared SQLite.
  • ~100 ms commit window — non-idempotent tools must never be replay:"safe".
